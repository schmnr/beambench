# CLI audit, September 6, 2026

The audit found and corrected defects in machine connection handling, macro confirmation, offline output, profile persistence, and scripting behavior. Changes are local release preparation on top of `65b2b10f` and the existing app review fixes. The app version remains 0.2.18. No release, website deployment, or feedback report submission was performed.

This was an audit of existing command correctness, not a claim of full desktop feature coverage. The subsequent [feature coverage check](./2026-09-06-cli-feature-coverage.md) identifies missing CLI wrappers and desktop workflows that are not exposed through either the CLI or HTTP API.

## Scope and method

Reviewed the command parser and handlers for agent, project, export, machine, camera, preview, vector, design, diagnostics, feedback, profile, asset, job, console, material, macro, import, ports, and version. Followed shared API and service paths where command behavior depends on them.

The executable regression suite runs the built CLI as a subprocess. Each test has isolated project files, configuration, and data directories. HTTP tests use a local mock server on an ephemeral port; macro confirmation is also tested through the real API router. No physical controller was connected and no laser or motion command was sent to hardware. Feedback tests save a local report only.

## Confirmed defects and corrections

| Priority | Defect and consequence | Correction and evidence |
| --- | --- | --- |
| High | `job run --port B` treated an “already connected” error as success and could continue using the existing connection to A. | Stop on every failed connect response before opening or starting a project. Executable regression verifies no later API request occurs. |
| High | Macros sent raw G-code without the confirmation checks used by other CLI/API commands. A laser command later in a macro could be reached after earlier motion. | API checks raw G-code confirmation and the whole macro's laser requirements before its first send. CLI forwards the flags; router regression verifies both gates and an empty console. |
| High | Offline G-code export and dry-run used default emitter settings rather than the configured machine profile, and bypassed service output validation. | Share `prepare_gcode_export` with desktop export. Regression verifies S=100 for 50 percent power with S-max=200 and constant-power M3, plus missing profile, origin, empty output, failed mask planning, and machine-bounds rejection. |
| High | Local planning loaded legacy layers without the desktop's migration, so a legacy tool-color layer could remain enabled for output. | Extract a service loader that migrates without changing session state; desktop open and offline planning use it. Regression verifies legacy tool-only content is rejected as empty output. |
| Medium | Profile commands loaded and saved a second settings context, leaving the app's in-memory state stale and allowing later app saves to overwrite CLI changes. | Route profile operations through the running API; sparse PATCH bodies preserve unrelated live values. Executable regression checks the request and unchanged CLI-side settings file. |
| Medium | Preparing feedback with a project called the desktop open path, adding recent files and rewriting settings. | Load into a private diagnostic context without persistence side effects. Local report regression verifies the settings bytes are unchanged. |
| Medium | Relative paths sent to the app were interpreted from the app's working directory. | Resolve paths in the CLI before API requests. Regression covers input, save-as, and export paths, including parent traversal. |
| Medium | Preflight failure could exit successfully, and `job run --json` could print a report followed by a second JSON error. Streaming errors lost their details. | Fail nonzero with one complete report; preserve streaming failure/cancellation bodies. Executable regressions cover failed and warning reports. |
| Medium | A job that returned to Idle before the first poll could leave `job run` waiting indefinitely. | Treat unexpected Idle as interrupted output. Executable regression has a deadline and verifies a nonzero result. |
| Medium | Framing checked confirmation only after opening the supplied project. | Check flags first. Regression verifies no API request is made when confirmation is missing. |
| Medium | Vector exports without a destination discarded returned content while reporting success. | Write text formats and decoded PDF bytes to stdout, retaining JSON behavior with `--json`. Executable regression checks SVG and PDF redirection. |
| Medium | Local API calls could use proxy settings, choose a hostname that did not match the IPv4 listener, or ignore an incomplete response body. | Use the shared config path, IPv4 loopback, no proxy/redirects, and explicit response-read failures. Tests set invalid proxy variables and send a truncated success response. |
| Medium | Design retry checked uppercase `BUSY`, although the API returns `busy`. | Retry the actual busy code within the configured wait; never retry stale revisions. Executable regression covers both cases. |
| Medium | Negative coordinates could be mistaken for flags, and nonfinite numbers could serialize as null. A true-by-default profile flag could not be set false. | Accept signed numeric values, reject nonfinite values before dispatch, and parse explicit booleans. Parser regressions cover negative coordinates, NaN/infinity, scanning offsets, and false. |
| Medium | Camera cleanup could delete kept or recent renders, and reused names could overwrite a previous capture. | Unique render names, a distinct kept prefix, and cleanup limited to ordinary owned PNG files older than 24 hours. Regression checks kept, fresh, old, and unrelated files. |
| Low | Legacy API error strings were replaced by generic messages, and direct service errors lost structured codes/details. | Preserve both error forms. Human-output and JSON regressions cover them. |
| Low | Camera doctor treated a stale saved “API disabled” setting as failure even when the running API responded, and could report a different hostname from the one used. | Report the live endpoint consistently and mark the stale setting as a warning. Mock API regression verifies a usable live connection. |

G-code export also rejects the same resolved path for input and output. Validation errors occur before opening the output destination, so existing output is preserved when planning or placement fails. This does not add atomic replacement for a disk failure during the final write.

## Implementation boundaries

Shared behavior is concentrated in two existing service modules: planning now exposes its checked G-code preparation step, and persistence exposes loading/migration without opening a live project. CLI profile operations reuse the existing API. The generated agent guide now distinguishes macro management from confirmed execution.

No new controller protocol, machine feature, or unattended job service was introduced. The CLI still operates the app's current session. The [CLI reference](../cli.md) explains these boundaries and the resulting scripting contract.

## Documentation and release follow-up

Added `docs/cli.md` and linked it from the README. Regenerated `docs/AI_AGENT_WORK_SURFACE.md`. Updated the adjacent website repository's CLI guide, G-code output reference, supported exports, and CLI/app state explainer, along with their translations and next-release draft.

The following remain release verification tasks or explicit product limits:

- Physical controller operation and Windows/Linux runtime and packaging checks were not exercised here. Test the CLI with the matching release app on each supported platform.
- Offline G-code needs a saved profile. Current Position and rotary output need the connected app; User Origin needs a saved origin.
- `job run` stops for preflight advisories as well as failures; it does not expose an advisory acceptance override.
- Ctrl+C, terminal closure, or loss of API connectivity stops the client, not the app-owned job. Cancel through the app or `job cancel`.
- The local API operates the current session without a per-invocation job ownership identifier. Coordinate concurrent automation and desktop actions accordingly.
- Diagnostics are snapshots of the context supplying them. Offline feedback diagnostics do not inspect an in-memory connection owned by a separate running app.

These checks do not establish that the CLI is free of bugs. They provide executable coverage for the confirmed failures and make the remaining operational limits explicit.
